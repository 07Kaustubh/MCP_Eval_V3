# PIPELINE S4 — Verifier-Fails Analysis

Triggered by: `PIPELINE S4 — Tasks/<TASK_DIR>` followed by paste of verifier fails + trajectories already deposited into `Agent_Responses/`.

## Phase-readiness gate (run FIRST, before anything else)

```
python Validators/phase_ready.py --phase s4 --task Tasks/<TASK_DIR>
python Validators/parse_trajectories.py Tasks/<TASK_DIR>
python Validators/check_export_freshness.py Tasks/<TASK_DIR> --pin     # PIN FIRST
python Validators/check_criterion_dependencies.py Tasks/<TASK_DIR>
python Validators/check_oe_rubric_sync.py Tasks/<TASK_DIR>
```

**`check_export_freshness.py --pin` is the first thing S4 does, before any classification.**
S4 reads three inputs the operator can re-paste from the platform at any moment: the two
verifier exports and the rubric file. Pinning them records which bytes this pass reasoned
about. On any later invocation the bare command re-hashes and FAILS on drift, naming the
per-run counts that moved. Without the pin, a re-paste silently invalidates every count,
bucket call and all-failing set in the reports while `phase_ready` and `close_task` both
still say READY. This happened twice inside one session on Task 44 (pass 3 superseded at
16:18, pass 4 superseded at 18:20, the second moving Opus from 28/33/43/31/32/37 to
32/32/44/32/36/46 and shrinking the both-model all-failing set from six criteria to five).
**If the pin drifts mid-pass, stop and restart the classification loop. Never reconcile
by hand.**

`check_criterion_dependencies.py` is the passing-cell audit (see Procedure step 1b).
`check_oe_rubric_sync.py` enforces AGENTS.md rule 14's mirroring clause and must be
re-run after ANY rubric edit made during S4, not just at entry.

The first script refuses to proceed if 5/6/7 + 8_Verifier_Fails.txt aren't present.
The second parses real trajectories and writes `_aux/Trajectory_Stats.json` with measured `pass@1` + `avg_tool_calls_total`. This is the empirical ground for the verdict — no manual JSON parsing.

If `parse_trajectories.py` returns `REBUILD_CANDIDATE_DENSITY` or `REBUILD_CANDIDATE_DIFFICULTY`, S4 cannot save the task — the user must invoke `PIPELINE REDO`.

## What this phase does

For each rubric that failed across runs, classify the failure: rubric-invalid, judge-error, or legitimate model failure. Produce fix-lists for invalid rubrics and judge errors, and AF justifications for legitimate failures.

**Start from removal, not from justification (AGENTS.md rule 21).** `Docs*/9_Common_Error.md` is explicit: for a criterion failing all completed runs, *"If and only if we can vehemently defend the existence of this criterion, should we keep it. Otherwise, we need to remove it."* Argue the removal case for every all-failing criterion before writing a word of justification. If the defence is not one you would volunteer to a reviewer unprompted, cut the criterion. The 5-point checklist is that test, not a formality to clear on the way to writing prose.

## Procedure

0.5. **Trajectory hard gates (v12 T2 + T3 — run BEFORE classification).**

   **T3 — Error Rate Gate:** Count the number of runs in `Agent_Responses/` that errored out (did not complete to a verifier-evaluable state). If the count is **≥ 3**, the task FAILs the Error Rate sub-dim per QC spec — at most 2 erroneous runs are allowed (need at least 4 successful runs). Record in `_aux/Council_Reports/S4_verdict.md`:
   ```
   ## Trajectory T3 — Error Rate
   Erroneous runs: <count>/6. Verdict: PASS (< 3) | FAIL (>= 3).
   ```
   On FAIL, STOP and tell the user — the task cannot be evaluated meaningfully; re-run trajectories.

   **T2 — Agent Failure Rate Gate (pass@1 ≤ 40%):** Across the SUCCESSFUL (non-error) runs, count how many passed ALL valid rubrics. The pass rate = passed_runs / completed_runs must be ≤ 40% (i.e., for 6 runs with 0 errors, at most 2 may pass everything; for 4 successful + 2 errors, at most 1 may pass everything). Record:
   ```
   ## Trajectory T2 — Agent Failure Rate
   Runs passing all rubrics: <count>/<completed>. pass@1: <pct>%. Verdict: PASS (≤ 40%) | FAIL (> 40%).
   ```
   On FAIL, the task is "Too Easy" per QC spec — STOP and route to `PIPELINE REDO` (the task needs harder levers).

1. **Build the rubric x run matrix.** For each rubric in `7_Rubrics.json` and each run in `Agent_Responses/`, mark pass / fail / not-evaluated. Identify rubrics that failed all completed runs (AF rubrics) and rubrics that failed some runs (partial fails).

1b. **Audit the PASSING cells for structural inconsistency (v22 — mandatory).**

   The rest of this phase is fail-driven, which means a criterion that passes *for the
   wrong reason* is invisible to it. Run:
   ```
   python Validators/check_criterion_dependencies.py Tasks/<TASK_DIR>
   ```
   It infers dependency edges from criterion text and reports every cell where a
   dependent criterion PASSED in a run where its antecedent FAILED. Those gradings are
   not merely generous, they are impossible: the artifact the dependent grades on did
   not exist in that run.

   Any hit is an **Overly Broad** rubric defect (Bucket 1), not a judge error. Bind the
   dependent's subject to the antecedent's artifact, in both title and evidence, and
   describe the artifact by its content rather than by a criterion number so the binding
   survives renumbering.

   Origin: Task 44 shipped a West-cluster owner criterion that passed 6/6 on Gemini while
   the criterion requiring the West coverage item to exist passed only 2/6. It cleared
   S3, AUDIT, FINAL and four S4 passes and was caught by an operator reading the matrix
   by eye. The lever the pair was built to carry was diluted the whole time: an agent
   could bank the owner credit on a comment written to a pre-existing record.

2. **For EVERY failing rubric, walk the trajectory BEFORE classifying.** Trajectory analysis is what distinguishes the three buckets — without it, you cannot tell a judge error from a legitimate fail or from a rubric-invalid case. Skipping the walk and classifying from the verifier text alone is the most common S4 defect.

   Per failing rubric, build a trajectory walk record covering ALL 6 runs (or however many completed):
   - **Relevant tool calls.** Every tool call across the runs that touches the rubric's subject (e.g., for "Agent sends email to robert.hayward@..." → list every `email_send` call in every run with recipient, subject, body excerpt).
   - **Parameter values.** Exact parameters the agent used (recipient, subject, body content, IDs, amounts, dates).
   - **Tool response.** Did the call succeed? What did the tool return? Was the artifact created with the expected values?
   - **Rubric criterion comparison.** Walk the rubric's criterion text and decide whether the trajectory evidence satisfies it — with the rubric's flexibility convention applied ("approximately" tolerates rounding; "(or similar)" tolerates phrasing variants; exact-match values must match exactly).

   ONLY AFTER the trajectory walk, classify into ONE of three buckets. **Every bucket entry MUST carry a trajectory citation in the form `Run X, tool call Y: <parameter values>` (or `Run X: action not attempted` for absence-of-action) — not just Bucket 2.**

   ### Bucket 1 — Rubric Invalid
   The rubric is the problem. Signs:
   - Outcome too strict (expects exact value, agent reported equivalent rounded value).
   - Outcome bundles two independent facts that pass / fail separately.
   - Process rubric punishes a valid alternative path.
   - Process rubric covers a property an Outcome already proves.
   - Phrasing fails a valid agent expression (e.g., expects exact phrase, accepts no synonyms).
   Trajectory citation required: name the trajectory step that produced the valid alternative the rubric did not accept (e.g., `Run 2, tool call 14: agent sent email with subject 'rate-lock review' — rubric expected exact phrase 'rate lock expiration review'`).
   Action: write the fix to `_aux/Council_Reports/S4_fixes.md` with a before / after, the trajectory citation, and reasoning.

   ### Bucket 2 — Judge Error
   The rubric is correct. The agent's trajectory shows it actually satisfied the rubric. The judge misread. Action: log to `_aux/Council_Reports/S4_judge_errors.md` with the trajectory citation (run #, tool call #, parameter value) proving the agent satisfied the rubric.

   ### Bucket 1b — Phrasing-Induced Misgrading (v22)
   The rubric is *technically* correct and its evidence field even disclaims the thing the
   judge demanded, but the TITLE's wording reliably induces the same misreading. Treat as a
   **Bucket 1 rubric defect and fix it**, do not file it as a judge error.

   **Threshold.** Reclassify from Bucket 2 to Bucket 1b when the same misreading appears on
   **3 or more cells**, OR on **both models**. Below that, Bucket 2 and a per-cell appeal is
   the right call.

   Rationale: a judge error you appeal once is cheap; a title that mis-grades on a third of
   its cells will keep doing so on every future export, and an appeal cannot fix it. The
   Rubrics-Eval severity ladder scores this as Moderate Overly Specific, which costs the
   Rubric Quality sub-dim, so leaving it in Bucket 2 protects the appeal count at the cost
   of the score.

   Fix pattern: delete the offending qualifier from the title rather than restating it, lift
   the disclaimer out of the evidence field into the title, and make the FAIL list exhaustive
   (`FAIL only if ...`). **Then re-grade every cell of that criterion by hand against the
   trajectories before shipping the edit** — an exhaustive FAIL list is easy to write too
   narrowly and silently gut the criterion.

   Origin: Task 44 criteria 58 and 59. Both carried evidence text saying the record
   identifier was "not required"; the grader demanded it anyway on 5 and 3 cells. Filed as
   judge errors in pass 4, which let two Moderate defects ship until an operator review
   reclassified them.

   ### Bucket 3 — Legitimate Model Failure (AF Justification)
   The rubric is correct. The agent really did fail. This is desired difficulty. Trajectory citation required: name the trajectory step where the agent went wrong (e.g., `Run 3, tool call 8: agent reported gross $186,350 instead of net $117,000`) OR `Run X: action not attempted` if the agent never tried the action.

   **Pre-write 5-point checklist (v15) — ask all 5 BEFORE writing the AF justification.** If any answer is NO, the rubric is the problem (Bucket 1), not the model. Reclassify and fix the rubric, do not write an AF justification.

   1. Is the criterion self-contained, atomic, and grounded in the universe's ground truth? (Judge can evaluate without external lookup; one independent claim; values exist in `_aux/Universe_Split/`.)
   2. Is it flexible enough to allow valid alternative approaches without unfairly penalizing the agent? (E.g., if prompt says "get Emeka up to speed", Slack is just as valid as email.)
   3. Is the criterion actually required by the prompt, rather than asking for something extra? (Re-read the prompt; trace the criterion back to a specific ask.)
   4. Does it use real tool names and valid parameters? (Verify against the universe-correct tool catalog (Brookfield: `Brookfield_Base_Universe/8_Server_Tools_Details.json`; KeyStone: `Mortgage_Base_Universe/6_Server_Tools_Details.json`; MoveOps: `MoveOps_Base_Universe/6_Server_Tools_Details.json`; StarPM: `StarPM_Base_Universe/7_Server_Tools_Details.json`); `search_crm` is not real, `crm_search_contacts` is.)
   5. Could a capable agent realistically pass this task? (If 0 of 6 runs passed despite a valid approach, the rubric may be unachievably strict.)

   If all 5 = YES → proceed to Bucket 3, write the AF justification.
   If any = NO → the rubric is the problem, not the model. Reclassify as Bucket 1 (Rubric Invalid) and add a fix to `_aux/Council_Reports/S4_fixes.md`.

   **Reference examples** (from the QC docs — patterns to emulate / avoid):

   GOOD AF justifications (cite the concrete failure mode):
   - "The agent consistently failed to identify the correct coordinator responsible for the DOT gap. This reflects a real reasoning failure that required cross-service inference."
   - "All runs sent the email to noah.fitzgerald@greenstack.com instead of noah.fitzpatrick@axiom.com. This entity confusion is the intended failure mode for the task."

   BAD patterns (these reveal a rubric issue and require a reclassification):
   - "Agent never used search_crm tool" → `search_crm` is not a real tool; rubric must be updated to use the real tool name (`crm_search_contacts`).
   - "Agent never included the exact phrase X" → if the same idea has multiple valid expressions, the rubric is over-specific; rewrite with `(or similar)`.
   - "Agent notified Emeka via Slack instead of email" → if the prompt only said "get Emeka up to speed", Slack is valid; the rubric improperly locks in a channel.
   - "Agent didn't update all 9 tickets" → first verify ground truth requires all 9; if so, write one atomic rubric per ticket rather than bundling.

   Action: write the AF justification using the template in `Reference/Linter_Playbook.md` — two to four sentences, no em-dashes, no references to guides / specs / frameworks, first-person, cites the concrete data fact and the specific reasoning gap. Save to `_aux/Council_Reports/S4_AF_justifications.md`.

   **All-Failing Rubrics sub-dim scoring (mandatory per v11):** after all failing rubrics are classified, compute the Bucket 1 ratio = `Bucket 1 count / total failing rubrics count`. Apply the threshold:

   | Bucket 1 ratio | All-Failing Rubrics sub-dim score | Verdict |
   |---|---|---|
   | > 50% | **1/5 (FAIL)** | Most all-failing rubrics are caused by invalid rubric design, not by genuine task difficulty. The rubric set itself is the problem. |
   | 25-50% | **3/5 (NON-FAIL)** | A meaningful fraction of failures trace to rubric issues; investigate the rubric quality. |
   | < 25% | **5/5 (PASS)** | Most failures are legitimate model failures or judge errors. The rubric set is sound. |

   Record the score in `_aux/Council_Reports/S4_verdict.md` under a new `## All-Failing Rubrics sub-dim` section with the Bucket 1 ratio + the assigned score + brief justification citing the failing rubrics involved.

   This closes the Rubrics-Eval "All-Failing Rubrics sub-dim defers to verifier stage" gap — the verifier stage IS S4, and v11 makes the scoring explicit instead of leaving the sub-dim permanently at "N/A → 5".

3. **Confirm classifications against the universe.** For every Bucket 1 / Bucket 2 classification, re-grep `_aux/Universe_Split/` to confirm the rubric value vs the agent's trajectory value. Council A handles this if any classification is uncertain.

4. **Update the Hardness Plan calibration.** Compare the stump hypothesis predictions in `_aux/Hardness_Plan.md` against the actual AF rubrics:
   - Predicted + actually failed → confirm in `Tasks/_meta/Stump_Hypotheses.md`.
   - Predicted + did not fail → over-predicted (lever was weaker than expected).
   - Not predicted + failed → under-predicted (which lever did we miss?).
   Append the calibration delta to `Tasks/_meta/Hardness_Patterns_Log.md`.

5. **Run the justification voice gate on the AF batch** before declaring the phase complete. AF justifications go to the platform reviewer; they must pass `check_justification.py` with exit 0:
   ```
   python Validators/check_justification.py Tasks/<TASK_DIR>/_aux/Council_Reports/S4_AF_justifications.md
   ```
   Skip this step only if Bucket 3 produced zero AF justifications (no legitimate model failures). If the file exists and the script returns non-zero, revise the AF justifications (strip every forbidden term per the per-hit report) and re-run until clean. Do NOT ship an AF batch that fails the voice gate.

## Exit criteria

- Every failing rubric classified into exactly one bucket.
- Bucket 1 fixes drafted in `_aux/Council_Reports/S4_fixes.md`.
- Bucket 3 AF justifications drafted in `_aux/Council_Reports/S4_AF_justifications.md` following the strict style (concise, human, no em-dashes, no references to guides) AND `python Validators/check_justification.py Tasks/<TASK_DIR>/_aux/Council_Reports/S4_AF_justifications.md` exits 0 (skip only if the file was not authored because Bucket 3 was empty).
- `_aux/Council_Reports/S4_verdict.md` exists with the matrix + classifications.
- `python Validators/check_export_freshness.py Tasks/<TASK_DIR>` exits 0, proving every number in the reports describes the export still on disk. **Re-run this last, immediately before declaring the phase complete** — the operator may have re-pasted while the pass was in flight.
- `python Validators/check_criterion_dependencies.py Tasks/<TASK_DIR>` exits 0, or every hit is fixed as a Bucket 1 Overly Broad defect.
- `python Validators/check_oe_rubric_sync.py Tasks/<TASK_DIR>` exits 0, re-run after any rubric edit made during the pass.
- `python Validators/check_rubric_antipatterns.py Tasks/<TASK_DIR>` exits 0. **Re-run after EVERY rubric edit**, including edits made to fix another finding; this gate exists because a closed MODERATE was reintroduced by exactly that route.
- `Tasks/_meta/Stump_Hypotheses.md` updated.
- `Tasks/_meta/Hardness_Patterns_Log.md` updated.

## STOP gate

This phase ends here. End your response. The user applies Bucket 1 (Rubric-Invalid) fixes to `7_Rubrics.json`, submits Bucket 3 (Judge-Error) AF justifications to the platform, and re-runs the platform verifier if fixes were made.

Three next-trigger paths:
- Fixes applied and re-running platform → user uploads, runs trajectories, re-invokes `PIPELINE S4 — Tasks/<TASK_DIR>` (paste new verifier fails) in a fresh chat if any fail.
- Task came back failing difficulty (pass@1 > 40%) or density (< 40 avg tool calls) → `PIPELINE REDO — Tasks/<TASK_DIR>` in a fresh chat — full rebuild.
- Everything shipped clean → EXIT. Append any novel finding to `Tasks/_meta/Learnings.md` before closing.

Do NOT loop S4 inside this chat.

## V4 (StarPM) dual-model S4

V4 tasks are verified on TWO models (Opus 4.8 + Gemini). Evals_starpm/4 mandates: "Run this eval once per model."

- Inputs replace `8_Verifier_Fails.txt` with `8a_Verifier_Fails_Opus.txt` + `8b_Verifier_Fails_Gemini.txt`, and `Agent_Responses/Run*.json` with `Agent_Responses/Opus/Run{1-6}_Trajectory.json` + `Agent_Responses/Gemini/Run{1-6}_Trajectory.json`. `Validators/phase_ready.py --phase s4` enforces this shape for starpm tasks.
- `Validators/parse_trajectories.py` discovers the per-model layout automatically and emits per-model pass@1 + density in `_aux/Trajectory_Stats.json`. pass@1 <= 40% and density >= 40 avg tool calls apply PER MODEL; a task passing on Gemini but trivially solved by Opus (or vice versa) is a difficulty failure for that model's run set.
- Run the full S4 classification loop TWICE (once per model): bucket every failing rubric per Evals_starpm/4 taxonomy, walking that model's trajectories. Write `_aux/S4_<bucket>.md` findings tagged with the model name.
- For QC-feedback-stage V4 tasks, `python3 Validators/qc_verdict.py parse|classify|audit <task_dir>` structurally parses `QC_Feedback_Verdict.txt` + the 9/10/11 dispute trio and cross-verifies every cited atom against the task SSOT; use `audit` output to ground every AF justification in a verifiable citation.
