## Procedure

1. **Read the inputs above.** Internalize the persona's voice from the brief and the V3 reference prompts. Internalize the levers selected in `Hardness_Plan.md`.

2. **Draft `5_Prompt.txt`.** Plain prose, persona's voice, 500-word cap, no em-dashes, no tool names, no MCP-server names, no internal IDs, no pre-solving. Engineer the selected hardness levers into the situation — each lever should appear naturally as part of the persona's framing, not as an obvious test hook.

2a. **(StarPM V4 only) Prompt-authoring guidance — spec-cited authoring bar.** `[PROJECT POLICY — cites no spec; step 2a scoping and structure authorized by plan §7.4]` Skip this step entirely for Brookfield, Keystone, and MoveOps. For StarPM, the draft from Step 2 must clear the six spec-cited requirements below before Step 3 (validator). Each requirement grounds a QC spec sub-dimension from `Docs_starpm/7_QC_Spec_Doc1.json` and `Docs_starpm/8_QC_Spec_Doc2.md`.

   - **Cross-service investigation across ≥ 3 services (cites §4.1 — Prompt → Tool use and Cross-service requirement):** the prompt must require the agent to investigate across at least three StarPM services (from airtable, contacts, gcalendar, gmail, hubspot, linear, quickbooks, slack) to reach the correct answer. §4.1 Pass (5) requires investigation across 2+ services; the ≥ 3 target sits above the spec floor to lift projected tool-call density above §4.9 (Trajectory → Tool Call Count) organically. Grep-verify against the Base Investigation Surface fields produced in HARDNESS Step 6a.
   - **Not pre-solved (cites §4.2 — Prompt → Investigation):** the prompt must not tell the agent the root cause or hand it the answer. §4.2 Fail band disqualifies prompts that "tell agent the root cause and no investigation is needed"; §4.2 Pass (5) requires the prompt to "clearly require investigation, and it logically follows from investigation." Verify by reading the prompt back to yourself — if a competent reader can name the answer from the prompt alone, the prompt is pre-solved.
   - **One cohesive situation (cites §4.3 — Prompt → Coherence):** every ask in the prompt must trace back to a single business situation. §4.3 Fail band disqualifies bolt-on requests where "removing a sentence doesn't change the rest"; §4.3 Pass (5) requires "One cohesive situation; stacked asks all tie back to the same purpose." Verify by removing each sentence — if the remainder still makes sense standalone, that sentence is a bolt-on and must be rewritten to feed the core situation.
   - **Not command-list style (cites §4.4 — Prompt → Contrived / Unnatural Prompts):** the prompt must not read as a mechanical step-by-step instruction sequence. §4.4 Fail band explicitly flags "Prompts written as step-by-step command lists ('First search emails, then check CRM…')" as contrived; §4.4 Pass (5) requires natural persona voice. Verify by reading the prompt aloud — if it sounds like a checklist rather than a real person's request, rewrite in natural persona voice.
   - **Tight identifiers grep-verified against `_aux/Universe_Split/` (cites §4.5 — Prompt → Truthfulness):** every tight identifier in the prompt (channel names, document IDs, ticket IDs, entity names, addresses, unit numbers, amounts, dates) must be grep-verified to exist in the per-task universe. §4.5 Major fail band lists these as identifiers "passed literally into tool calls" that "don't tolerate near-matches"; a single wrong identifier is a Major factual error. Record the grep evidence in `_aux/Reasoning/prompt_design.md` per identifier.
   - **Persona voice anchored on a specific `QC_Tasks/V4_Tasks/QC_Passed/` exemplar (cites §4.6 — Prompt → Persona):** pick one QC-passed reference task in `QC_Tasks/V4_Tasks/QC_Passed/` whose persona matches or closely matches the current task's assigned persona, quote a 2-4 sentence excerpt as the voice anchor, and match its tone / register / length distribution. §4.6 Fail band flags "The prompt written by the CB does not read like it could have been written by the persona selected"; §4.6 Pass (5) requires the prompt "aligns with the persona selected." Record the exemplar file path + quoted excerpt in `_aux/Reasoning/prompt_design.md` under a `## Persona voice anchor` subsection.

3. **Run the validator (cheap gate).**
   ```
   python Validators/validate.py --phase prompt --task Tasks/<TASK_DIR>
   ```
   Read `_aux/Validator_Reports/prompt.md`. If FAIL, fix every fail, re-run until clean.

4. **Spawn Council A — Grounding.** Follow `Reference/Council_Protocol.md`. The sub-agent extracts every concrete claim in `5_Prompt.txt` and verifies it against `_aux/Universe_Split/`. Output goes to `_aux/Council_Reports/S1_A_grounding.md`. Block on any ungrounded claim.

5. **Spawn Council B — Adversarial QC.** Follow `Reference/Council_Protocol.md`. Scores every applicable QC sub-dim from `Docs/7_QC_Spec_Doc1.json` against the prompt, attempts a second valid reading that flips a write action, and runs the adversarial sweep. Output goes to `_aux/Council_Reports/S1_B_adversarial.md`. Block on any Major / Moderate issue.

6. **Loop.** If either council blocks, apply fixes, re-run the validator, re-run BOTH councils. Loop until clean.

7. **Run the similarity gate against the prior-task corpus.** Both councils have cleared the prompt on quality; this gate checks it does not collide with prior submissions before we let it through to the platform linter (where a similarity hit costs the operator a round trip).
   ```
   python Validators/calc_similarity.py Tasks/<TASK_DIR>
   ```
   The script writes `_aux/Similarity_Report.json` with the top matches against every prior `5_Prompt.txt` in `Tasks/` and the V3 reference prompts. Read the report.

   | Score band | Action |
   |---|---|
   | < 40 | PASS. Proceed to step 8. The composite is multiplicatively weighted by contextual differentiators (persona / business function / universe) — a sub-40 score means the prompt is either genuinely lexically distinct OR has strong contextual differentiators that would justify invalidation at S1.5 if the platform linter ever flagged it. Log the top match + composite to `_aux/Reasoning/prompt_design.md` for the record. |
   | ≥ 40 | STOP. PIVOT mandatory — the composite is high EVEN AFTER contextual weighting, meaning constants align with a prior task and the structural similarity is genuine (not just surface lexical overlap). Do NOT proceed to step 8. Re-draft the prompt using `Reference/Similarity_Pivot.md` (pick the smallest combination of the 6 levers that breaks the match while preserving the Hardness Plan levers), then loop back to step 3 (validator) + step 4 + step 5 + step 7 against the fresh draft. Log the pivot to `Tasks/_meta/Similarity_Log.md` with the date, top-match reference, composite + per-dim scores, and the resulting similarity score. |

8. **Strict veteran audit (conditional auto-fire — Track F v21).** AUDIT auto-fire is MANDATORY when ANY of these holds: (a) Council B used any NON-FAIL band justification on any sub-dim, (b) `validate.py --phase prompt` exited 0 but emitted ≥1 WARN, (c) `verify_universe_atoms.py` exited 0 but emitted any edge-case-needs-LLM-judgment flag, (d) similarity composite ≥ 35 (sub-threshold but near pivot band), (e) prompt was revised in this S1 pass (lengthy iteration history). OTHERWISE — Council B uniformly 5/5 with no bands invoked AND validator exit 0 zero WARN AND atom-verifier clean AND similarity < 35 AND first-pass draft — AUDIT auto-fire is OPTIONAL (operator decides; default skip and rely on on-demand AUDIT before platform upload). On-demand AUDIT in a fresh chat remains unchanged in either case. Spawn the audit sub-agent (`oracle`) using `Reference/Sessions/AUDIT.md` with `--phase prompt`. Save to `_aux/Council_Reports/AUDIT_prompt.md`. AUDIT applies the STRICTEST QC interpretation — 5/5 is the only acceptable score on every applicable sub-dim (no NON-FAIL band justifications), density bar 50+ midpoint (not 40 floor), every "should" reads as "must". This catches what Council A + B + similarity gate missed.

   | Verdict | Action |
   |---|---|
   | `PASS (STRICT)` | Proceed to step 9 (final report). |
   | `REVISE` | Apply the audit's per-issue fixes IN PLACE in `5_Prompt.txt`. Re-run step 3 (validator) + step 4 (Council A) + step 5 (Council B) + step 7 (similarity gate) + step 8 (AUDIT) against the revised prompt. Iteration cap: **3 REVISE rounds**. After 3, end your response with the full audit issue list and escalate to the user. |
   | `REBUILD` | The prompt has structural issues a fix-in-place cannot repair (e.g., the prompt's framing actively blocks 3+ Hardness levers, second valid reading flips multiple write actions). End your response with the audit's REBUILD recommendation and recommend `PIPELINE REDO — Tasks/<TASK_DIR>` in a fresh chat. |

9. **Final report.** Append a short verdict to `_aux/Reasoning/prompt_design.md` summarizing: which levers were engineered into the prompt, expected stump targets, council verdicts, the final similarity score with top match, and the AUDIT verdict.
