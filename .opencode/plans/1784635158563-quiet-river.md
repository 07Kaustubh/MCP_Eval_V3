## 2. Key Architectural Decisions (sign-off points)

**D1 — Minimal framework axis (ADOPT).** V4 differs from V3 at the *framework* level, not just universe level: +2 eval phases, dual-model, density floor 15 (not 40/50), new task shape. Add a single `framework_version` field per registry entry **plus** a `FRAMEWORKS` profile table keyed by version. Today the mapping is 1:1 (`brookfield→v3`, `keystone→v3.1`, `moveops→v2.1`, `starpm→v4`), so this is a lookup, not a task-rebinding refactor. This is the Oracle-blessed axis from `.omo/ulw-v4starpm-notepad.md` (L112-124), implemented minimally.

**D2 — Additive, gated-on-v4 (ZERO-REGRESSION INVARIANT).** Every new behavior (injection/submission phases, dual-model parsing, density-15, doc/eval reroute) executes **only** when `universe==starpm` or `framework_version=="v4"`. Existing universes never enter new code paths. For shared code that must be parameterized (e.g. `validate.py` OE param-trap check), the registry values for brookfield/keystone/moveops **reproduce today's behavior byte-for-byte** — proven by the wave-0 report-hash gate on every wave.

**D3 — Explicit-declare routing, fail-loud detect.** StarPM and Brookfield share `slack.*`/`linear.*` service tokens. `_aux/Universe.txt` written at S0 is SSOT; `detect_universe` remains a guard. Give `_STARPM_SIGNALS` strong non-overlapping tokens (hubspot+quickbooks+gcalendar+gmail + `@starpm.com` personas + `#make-ready`/`#owner-relations` + "Star Property Management") to beat the brookfield tiebreak bias (`universes.py:323-324`).

**D4 — Verdict logic universe-parameterized.** The 16 QC tasks are **Brookfield** fixtures (persona Anaya Wallace, `@brookfieldcpas.com`, BlackLine). The verdict engine cross-references each task's own universe SSOT (via its `Fact_Ledger`), never StarPM-hardcoded. The 16 tasks are the **acceptance corpus** for bucket-correctness, not StarPM universe facts.

**D5 — `code_hashes.txt` is an audit, not a gate.** We edit code by design, so code hashes change. The regression *gate* is (a) 48+ anchors green and (b) 7-task **report** hashes unchanged. `code_hashes` is regenerated per wave only to confirm *which* files changed matches intent (no stray edits).

## 6. Atomic Commit Strategy

- **Branch:** `starpm-v4-integration` off `OMEGA`. Never commit to `main`.
- **One squashed commit per wave** (7 total, W1-W7). WIP commits allowed intra-wave, squashed before the wave commit.
- **Gate-gated:** a wave commit lands **only** when its binary gate is green (`check_regression.py` PASS + wave-specific assertion). No red commits — history is bisectable and every commit preserves Brookfield behavior.
- **Message format:** `waveN: <summary>` + body listing the gate evidence (`anchors N/N · reports 21/21 · <wave assertion>`) and the touched-files audit set.
- **Reversible:** because every wave is additive/gated, any wave commit can be reverted without breaking earlier universes.
