# How to Generate 5/5 Tasks, Attempter's Guide (HarmonyGames)

This is the **mirror image** of the eval suite. The eval playbooks (`0_Injection_Quality_Eval`, `1_Prompt_Eval`, `2_OE_Eval`, `3_Rubrics_Eval`, `4_Verifier_Fails_Eval`, `5_Submission_Gate_Eval`) are the graders. This guide tells you how to **author** a task, Prompt → Oracle Events → Rubrics, so it scores **5 on every scored dimension** and clears every HARD GATE before it ever reaches a grader. It owns the **generation commands**; it does not redefine the rules in `[Docs/](../Docs/)` or `[Evals/](../Evals/)`. For the run/evaluation sequence, use `[How_To_Use_This_Eval.md](How_To_Use_This_Eval.md)`.

---

# The Generation Commands (copy-paste)

> **Why order matters:** the prompt is the root of the whole task. If the prompt is weak, the OEs and rubrics built on it must be redone. Treat prompt generation as the most critical step, re-verify feasibility, Persona ACL reachability, relative-date alignment, data consistency, and truthfulness many times, against the raw universe tables, before moving on.

> **Before running:** copy `Tasks_Template/` to a new `<task-name>/` folder at the repository root and fill `<task-name>/1_Business_Function.txt` and `<task-name>/2_Persona.txt` (Persona Key, Persona Email, Name, Role, Department copied EXACTLY from one `HarmonyGames_Base_Universe/4_Persona_ACL_Roster.json` entry — never infer the email from the name). Write generated artifacts to `5_Prompt.txt` → `6_Oracle_Events.txt` → `7_Rubrics.json` in the task folder.

## Command 2, Oracle Events Generation

```
Great, the prompt is approved. The OEs are the unordered critical-path tool-use steps a perfect agent would take, each one a tool call with the action, the tool, the parameters that matter, and the expected discovery. They are NOT the final answer text and NOT reasoning without a tool. Before generating, re-read the project docs (especially @Docs/2_Rubrics_Guidelines.md for the OE->rubric mapping and @Docs/9_Common_Error.md ), the QC spec @Docs/7_QC_Spec_Doc1.json @Docs/8_QC_Spec_Doc2.md , the Persona ACL rules @Docs/14_Persona_ACL.md , and the full tool catalog @HarmonyGames_Base_Universe/6_Server_Tools_Details.json , then re-read the universe data from each single service @HarmonyGames_Base_Universe/Services_Data/confluence @HarmonyGames_Base_Universe/Services_Data/contacts @HarmonyGames_Base_Universe/Services_Data/gcal @HarmonyGames_Base_Universe/Services_Data/gdocs @HarmonyGames_Base_Universe/Services_Data/gdrive @HarmonyGames_Base_Universe/Services_Data/github @HarmonyGames_Base_Universe/Services_Data/gmail @HarmonyGames_Base_Universe/Services_Data/gsheets @HarmonyGames_Base_Universe/Services_Data/gslides @HarmonyGames_Base_Universe/Services_Data/linear @HarmonyGames_Base_Universe/Services_Data/slack @HarmonyGames_Base_Universe/Services_Data/snowflake @HarmonyGames_Base_Universe/Services_Data/trello (complete data: @HarmonyGames_Base_Universe/Services_Data/Base_Universe_Complete_Data.json ). High quality OEs pass every phase of @Evals/2_OE_Eval.md and score 5/5 on BOTH dimensions, OE Completeness and OE Accuracy. ## Command 3, Rubrics Generation

```
The prompt and oracle events are approved. Now generate the rubrics from the approved prompt @<task-name>/5_Prompt.txt and oracle events @<task-name>/6_Oracle_Events.txt . First re-read the rubric model and rules @Docs/2_Rubrics_Guidelines.md @Docs/3_Rubrics_One_Pager.md @Docs/12_Always_Failing_Rubrics.md @Docs/9_Common_Error.md , the QC spec and severity taxonomy @Docs/7_QC_Spec_Doc1.json @Docs/8_QC_Spec_Doc2.md , the Persona ACL rules @Docs/14_Persona_ACL.md , the tool catalog @HarmonyGames_Base_Universe/6_Server_Tools_Details.json , and re-read the universe data services under @HarmonyGames_Base_Universe/Services_Data (complete data: @HarmonyGames_Base_Universe/Services_Data/Base_Universe_Complete_Data.json ) to verify every literal. The task JSON stores four fields per rubric: title (the criterion text), category, justification, and evidence. Use only two categories, Outcome (mandatory) and Process (optional and rare); every category value must be exactly Outcome 1.1, Outcome 1.2, Outcome 2.1, or Process. Build Outcome first: each write OE -> an Outcome 1.1 rubric (+ a 1.2 rubric if the content has specific requirements); each fact the user asked to be told -> an Outcome 2.1 rubric. Add a Process rubric ONLY if it passes all three conditions (required by every valid solution path; a stricter Outcome rubric cannot capture it; it verifies behavior, not an execution trace); prefer ZERO Process rubrics and never let Process exceed 40% of the set. High quality rubrics pass every phase of @Evals/3_Rubrics_Eval.md and score 5/5 on all sub-dimensions with ZERO Major and ZERO Moderate issues. After drafting, run the rubric eval using multiple subagents and revise until every sub-dimension is a clean 5/5 with zero Major and zero Moderate. Keep the number of subagents equal to the count of to-dos in that eval's to-do list, one subagent does a very deep evaluation of exactly one to-do. Keep these on TOP priority, re-checked multiple times: AGENT-CENTRIC PHRASING — every criterion is "The Agent ..." + action + context, with NO tool name in the title (tool names may appear ONLY in evidence and must exist in the tool catalog, and evidence must never be stricter than the criterion); ATOMICITY — one independent pass/fail check per rubric (split "email AND post a note"); this is the #1 QC failure pattern; SELF-CONTAINMENT — embed every email, amount, name, ID, date, count, channel in the title, no catch-alls like "relevant accounts" or "or another channel"; CORRECTNESS — every literal traces to the prompt or universe data, persona-scoped values, dates resolved from 2026-02-28; OVER-SPECIFICITY / VALID-PATH PRESERVATION — a rubric's specificity must not exceed the prompt's; a goal-level ask ("notify the team") must stay method-agnostic and must not be locked to one channel/format (channel or structured-value lock-in that would fail a valid alternative path is a Major issue); FLEXIBILITY — "approximately" for calculated/rounded values only, exact match for IDs/dates/counts/emails, "(or similar)" only for free-text; COMPLETENESS — forward (every explicit ask has a rubric) and reverse (no rubric goes beyond the prompt); NO OVERLAP/REDUNDANCY/CONTRADICTION between pairs. Also ensure the rubrics pass the QC spec docs. When every sub-dimension scores a clean 5/5 with zero Major/Moderate, write the final rubrics (JSON array) to @<task-name>/7_Rubrics.json and give me the per-sub-dimension scorecard with the severity tally and evidence. Keep the rubric formatting like the @Tasks_Template/7_Rubrics.json sample. One important thing: there are two kinds of rubrics — negative ones whose title starts with "The Agent does not ..." and positive ones "The Agent + context (without a 'does not')". Do NOT ship negative rubrics: either convert each negative rubric into a positive one with sound logic and reasoning (not just reworded), or drop it. Focus on creating positive, correct rubrics only.
```

# Command to request a harder prompt

```
We need to ensure the prompt is really complex and hard. A hard and complex prompt is one that is based on multiple and many tightly interconnected scenarios, artifacts, storylines, etc., because if our asks come from tightly coupled and really dense multiple scenarios then there is a high possibility of causing model failure. So please re-read the universe data in very deep detail across @HarmonyGames_Base_Universe/Services_Data and try to find those tightly coupled and complex areas from where we can draw our asks. Do deep research to come up with many such asks based on dense, coupled, and complex areas that span multiple services (not just 3-4, even a lot more than that) — e.g. a Linear ticket state reconciled against GitHub PRs and Slack channels and a spec doc, or a past deal traced across Gmail threads, Slides/Drive decks, and exec channels. Please act like a machine learning and AI researcher who has the ability to read, understand, and find those areas where we can stump the model. Be really expert. Our motive is to have the hardest prompt ever, targeting the nerves of the entire universe across multiple scenarios and areas involving multiple tools and services, while staying fully feasible under the assigned persona's ACL scope and truthful to the data.
```

## The Iron Laws

1. **Everything must be grounded in the universe.** Every name, email, amount, ID, status, relationship, channel, repository, and date you write must exist in `HarmonyGames_Base_Universe/Services_Data/` (or the task-specific `3_UniverseDataForThisTask.json`). If you can't find it in the data, don't write it. Tool names are grounded in `HarmonyGames_Base_Universe/6_Server_Tools_Details.json`.
2. **The fixed "today" is 2026-02-28 (Saturday), America/Chicago.** Every relative time reference must resolve against this date *and* land in a window that actually has data. The active injection window is 2026-01-01 → 2026-02-28. February month-end close is just beginning and Q1 does not end until March 31, so keep this mid-quarter state coherent.
3. **Persona ACL is active and non-negotiable.** `2_Persona.txt` must match one `4_Persona_ACL_Roster.json` entry exactly (Persona Key, Email, Name, Role, Department). Derive the persona-scoped service set live from the `Docs/14_Persona_ACL.md` Access matrix (do not hardcode — scoped reads are on Gmail, Slack, GCal, and Contacts unless the doc changes). Every required scoped fact needs a concrete reachability path for the assigned persona (mailbox ownership; Slack membership/public visibility; calendar ownership/share/invite; Contacts visibility) — or the intended outcome is an affirmative denial, or an explicitly authorized unscoped alternate. Universe Explorer author god-mode never proves reachability; writes are never ACL-blocked.
4. **Complexity floor.** The prompt must need more than 15 necessary calls, 2+ genuine services doing real work (40+ calls and 3+ services are authoring targets), multiple meaningful writes, and real information friction. A single-service investigate-then-email task fails as Too Easy.

Grade-to-the-lowest: the prompt and rubric dimensions take your **lowest** sub-score. A single fail anywhere fails the component. There is no "average." When every phase in `[../Guide/How_To_Use_This_Eval.md](How_To_Use_This_Eval.md)` passes with zero hard failures, the task is submission-ready.
